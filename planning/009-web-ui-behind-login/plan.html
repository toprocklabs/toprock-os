Plan · Feature 009

CRM web UI behind login

Make the CRM usable at the Vercel URL — phone, any laptop — by opening it behind the existing username/password session, with the proxy enforcing that session on every path and the login form rate-limited. The agent API, client SOW pages, and the SELECT-only MCP role do not change.

Supersedes plan 007 — the "no web UI at all" half. 007's data-migration tooling and its default-deny, fail-closed reasoning stand; this plan keeps both and changes what "deny" means for signed-in people. Plan 008 is untouched.

Why reverse 007

007 named its own cost: no phone access, no access from a machine without the repo, and onboarding anyone means handing over a database credential. That friction bit. The ask now is to use the CRM at toprock-os.vercel.app like a normal web app. Of the options considered — app login + hardening, a second Vercel project behind Vercel Authentication, or an IP allowlist — the app login was chosen: one deployment, no extra cost, works from any network.

What we give up

007's strongest property was that production had no authentication surface at all. After this plan it has one: a public /login form. Everything below exists to make that form expensive to attack and to make sure it is the only door — no page, data request, or server action is reachable without a valid session, even if a future page forgets its own check.

The new surface model

Three tiers instead of two. The decision stays a pure, tested function in src/lib/public-surface.ts.

Default deny is preserved: a new route is signed-in-only unless deliberately added to the public list. What changes is that "deny" now means "log in first" rather than "404 to everyone".

The static placeholder at / (PR #8) is removed — / is the dashboard again and simply redirects anonymous visitors to /login.

Mechanism: session gate in proxy.ts

Today every page calls requireUser() and every action goes through defineAction — correct, but per-route. The proxy adds a second, structural check that runs before any route renders, so one forgotten guard can't leak a page.

// src/proxy.ts (sketch)
export async function proxy(request: NextRequest) {
  const surface = classifyPath(request.nextUrl.pathname); // "public" | "login" | "private"
  if (!isWebUiEnabled()) return lockdown(surface);        // 007 behavior, unchanged
  if (surface !== "private") return NextResponse.next();
  if (await verifySessionToken(request.cookies.get(SESSION_COOKIE)?.value)) {
    return NextResponse.next();
  }
  return request.method === "GET"
    ? NextResponse.redirect(new URL("/login", request.url))
    : new NextResponse(null, { status: 401 });
}
  • verifySessionToken is extracted from src/lib/auth.ts so the proxy and getSession() share one JWT check (jose, HS256, AUTH_SECRET). The proxy runs on Node in Next 16, so no Edge constraints.
  • The proxy only checks the signature and expiry — it doesn't hit the database. Pages still call requireUser(); both layers must pass.
  • ?next= return-to after login is allowed only for same-origin relative paths starting with a single / (no open redirect).

The on/off switch

The web UI is opt-in per environment with CRM_WEB_UI=on. Absent or any other value → exactly 007's lockdown (404 wall). This keeps 007's fail-closed rule: a new environment, preview, or fork is locked until someone turns the UI on deliberately, and turning it off in an incident is one env change + redeploy.

Login hardening

ControlDetail
Attempt logNew login_attempts table: username, ip, succeeded, created_at, indexed on (username, created_at) and (ip, created_at). Postgres, not an in-memory map — Fluid Compute runs several instances, and a per-instance counter is trivially spread across them.
Per-username lockout≥ 5 failures in 15 min, counted since that username's last successful login → reject further attempts until the window rolls off. Rejected attempts are not recorded, so a lockout cannot be extended indefinitely. Message: "Too many sign-in attempts" — safe to distinguish, because the limit applies to any username string, real or not, so it reveals nothing about which accounts exist.
Per-IP limit≥ 20 failures in 15 min from one IP → reject. IP from x-forwarded-for first hop (Vercel sets it; not spoofable past their edge).
No user enumerationUnknown username still runs a bcrypt.compare against a fixed dummy hash, so timing and message match a wrong password.
Password flooruser:create requires ≥ 12 characters for new or reset passwords. Existing users are asked to reset before the switch is flipped. (The login form itself still accepts ≥ 6, so existing passwords keep working until reset.)
RetentionRows older than 30 days deleted opportunistically on each login attempt (one cheap indexed DELETE). No cron needed.

Cookie & response headers

  • crm_session stays httpOnly, Secure in production, SameSite=Lax, 14-day expiry. Lax still blocks cross-site POSTs to server actions; Next also checks the Origin header on actions.
  • Proxy adds X-Robots-Tag: noindex, nofollow to every response, and X-Frame-Options: DENY + Referrer-Policy: same-origin to signed-in and login responses (clickjacking on the login form and the app).
  • Sign-out everywhere = rotate AUTH_SECRET in Vercel and redeploy. Documented, not built (see out of scope).

Phases

Phase 1 — built, switch off

Gate, throttle, tests

Ship everything with CRM_WEB_UI unset. Production behaves exactly as today; the new paths are exercised locally with npm run build && CRM_WEB_UI=on npm start.

Phase 2 — table applied; passwords outstanding

Schema and credentials

Apply drizzle/0009_far_magus.sql directly — not db:push: the shared database holds five tables this schema doesn't define (brain_*, meeting*), and push offers to drop or rename them. Reset both users' passwords to ≥ 12 characters. Re-run npm run mcp:role -- --audit-only — the new table must not be readable by the MCP role.

Phase 3 — flip

Turn the UI on in production

CRM_WEB_UI=on in Vercel production only, redeploy, run the verification list. Rollback is removing the variable and redeploying.

Out of scope

  • 2FA / passkeys — worth a later plan if more users are added.
  • Per-session revocation (session table or users.session_version). AUTH_SECRET rotation covers the two-user case.
  • Password reset by email.
  • Multi-tenant authorization — still single-tenant, as today.
  • Custom domain.
