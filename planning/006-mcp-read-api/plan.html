Plan · Feature 006

Read-only MCP endpoint for external agents

Superseded by plan 008. While this was being built, a second agent independently shipped a different MCP at the same path (75fd50a, PR #4) — Streamable HTTP, twelve tools, and a write path through the /inbox suggestion queue. That implementation was merged to main and deployed first. Rather than revert working, reviewed code, the decision was to keep it and port this plan's security layer onto it: the SELECT-only Neon role, the connection split, and the public-surface wall. Plan 008 records what actually exists. The reasoning below — especially why MCP over a collection export or a raw connection string, and why no run_sql — still holds and still governs.

Let Grok Bot answer "what's the last thing we heard from Al?" and "who's stuck in negotiation?" from live CRM data — through eleven named, read-only tools at /api/mcp, never a database door and never a raw-SQL tool.

The ask, and why MCP

Grok Bot lives in Discord and gets asked CRM questions in natural language. Today it has no access to this database, so every answer is either a guess or a request for a human to go look. The questions that actually get asked are relational and filtered — "last thing from Al", "which deals are stuck in negotiation", "is GT Cabinets current on payments" — not keyword search over a document dump.

That shape has one honest answer: give the agent named tools that encode the joins in code, backed by live Postgres reads. Not a search index over stale exports, and not a connection string.

Options considered

OptionFreshnessPermission scopeBlast radius if leakedVerdict
1. MCP endpoint in the CRM Live — Neon queried per tool call Per-tool allowlist + SELECT-only role + bearer URL alone useless; a leaked bearer still reaches only eleven read tools; no users, no credentials Chosen
2. xAI Collection export Stale — hours/days without a sync job Soft: whatever went into the files The export is a broad CRM snapshot No — search over dumps can't do "stuck in negotiation"; high ongoing maintenance (export jobs, schema drift, re-upload)
3. Direct Neon connection string Live Role can be SELECT-only, but the agent holds a database door A wide credential in agent secrets; hard to audit No — low code, high ops risk; fights the "no run_sql" rule

Why not a generic run_sql tool. It is the tempting shortcut and the wrong one for v1. A Discord message is untrusted input; a model holding run_sql can be steered by it. You also cannot prove such a tool never touches users — the audit trail becomes "whatever SQL the model invented." Named tools move that proof from runtime to code review: the eleven queries below are the complete set of statements this endpoint can ever execute.

Architecture

Why a hand-rolled JSON-RPC handler

The endpoint is stateless: no sessions, no server-initiated messages, no subscriptions. The three methods that matter (initialize, tools/list, tools/call) plus ping are roughly 120 lines of envelope handling. Pulling in the MCP SDK to do that would add a dependency, a transport abstraction, and an SSE code path this route will never use, to a project that has deliberately stayed dependency-light. The protocol layer is pure and unit-tested instead.

Protocol surface

MethodBehavior
initializeEchoes the client's protocolVersion when it is one we know, else our default (2025-06-18). Advertises capabilities.tools only.
notifications/*No id → no response body. Returns 202 Accepted, per the JSON-RPC notification contract.
ping{}. Cheap liveness for the connector UI.
tools/listAll eleven tools with JSON Schema generated from their zod schemas via z.toJSONSchema() — one definition, no schema drift between validation and advertisement.
tools/callAllowlist lookup by name. Argument validation failures and unknown tools come back as isError: true tool results (the model can correct itself), not JSON-RPC errors (which abort the turn).
anything else-32601 Method not found.
GET / DELETE405 with Allow: POST. No SSE stream to open; compliant clients fall back to POST-only.

Responses are always application/json. The spec lets a server answer a POST with either JSON or an SSE stream; with no server-initiated messages to deliver, JSON is the honest choice.

Auth & fail-closed

  • Authorization: Bearer <MCP_BEARER_TOKEN>, compared with timingSafeEqual over SHA-256 digests so the compare is constant-time and length-independent.
  • Unset MCP_BEARER_TOKEN disables the endpoint entirely — 503, no database touched. A fresh clone, a preview deploy, or a forgotten env var yields a dead route rather than an open one. This is the single most important line in the feature.
  • A token shorter than 32 characters is refused at startup of the request, same as AUTH_SECRET.
  • 401 carries WWW-Authenticate: Bearer and nothing else — no hint about whether the token was absent, malformed, or wrong.
  • The token is not reused from AUTH_SECRET or any admin secret. Separate audience, separate rotation.

Public repo, private secrets. Shipping /api/mcp in a public repository is fine — the design is the security, not the obscurity. What must never enter the repo: DATABASE_URL, MCP_DATABASE_URL, MCP_BEARER_TOKEN. The production URL and call examples stay out of README.md too; they live in Vercel and in the connector config, which cuts casual probing without pretending it is a control.

The SELECT-only role

MCP_DATABASE_URL should point at a Neon role created like this. It is defence in depth: the tools contain no write statements, so this role exists to make a future mistake unable to become an incident.

npm run mcp:role              # provisions, then audits
npm run mcp:role -- --dry-run # print the SQL, touch nothing

scripts/setup-mcp-role.mjs issues exactly this, against the admin DATABASE_URL:

CREATE ROLE crm_mcp_ro WITH LOGIN PASSWORD '…';
GRANT CONNECT ON DATABASE neondb TO crm_mcp_ro;
GRANT USAGE ON SCHEMA public TO crm_mcp_ro;
GRANT SELECT ON public."companies" TO crm_mcp_ro;
GRANT SELECT ON public."contacts"  TO crm_mcp_ro;
GRANT SELECT ON public."deals"     TO crm_mcp_ro;
GRANT SELECT ON public."activities" TO crm_mcp_ro;
GRANT SELECT ON public."sales_tasks" TO crm_mcp_ro;
-- never granted: users, proposals, proposal_documents, payments,
-- stripe_subscriptions, suggestions, agent_runs, relationships,
-- project_repos, place_enrichment

Correction to the original draft: no ALTER DEFAULT PRIVILEGES. The first version of this plan ended with ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES, which would hand the MCP role read access to every table added in the future — the exact opposite of an allowlist. A later api_keys or user_tokens table would have become readable the moment it was created, silently. Grants are now enumerated per table, and adding one is a deliberate edit to READABLE_TABLES in the script.

The script then proves the result rather than asserting it, by asking Postgres what the role can actually do to every table in the schema — has_table_privilege, a catalog read, so the audit itself can never write:

  table                     select  insert  update  delete
  ----------------------------------------------------------
  activities                  yes     --      --      --
  companies                   yes     --      --      --
  contacts                    yes     --      --      --
  deals                       yes     --      --      --
  payments                    --      --      --      --
  proposal_documents          --      --      --      --
  proposals                   --      --      --      --
  sales_tasks                 yes     --      --      --
  users                       --      --      --      --
  …

Any unexpected privilege exits non-zero with <-- UNEXPECTED against the row. Re-runnable at any time as npm run mcp:role -- --audit-only, which is the honest answer to "is it still read-only?" months from now.

If MCP_DATABASE_URL is absent the endpoint falls back to DATABASE_URL, so the feature works before the role exists — but then only the code-level guarantees apply. Creating the role is a deploy step, not an optional nicety.

Tool catalog

Eleven tools. Every one is a SELECT. Every limit is clamped to 1–100 (default 20). Free-text arguments are only ever bound as parameters to ilike patterns.

Output shape

Each result is returned twice: as structuredContent (typed JSON, for clients that use it) and as a pretty-printed JSON block in content[0].text (for clients that only read text). Conventions inside that JSON:

  • Money as both value_cents and a formatted value — models are bad at dividing by 100 and good at reading $1,200.00.
  • Dates as ISO-8601 strings; days_since computed server-side where staleness is the point.
  • Free text (activities.notes) truncated at 2,000 characters with an explicit "…[truncated]" marker, so one pasted email thread cannot blow the agent's context.
  • id on every row, so the model can chain a search into a get_*.

Contact email and phone are exposed: they are the point of a CRM lookup, and the endpoint is bearer-gated to one internal agent. That is the one judgement call in the table above worth revisiting if the bot's audience widens beyond the team's Discord.

Prompt injection & blast radius

CRM notes are attacker-influenceable — a prospect can email text that ends up pasted into an activity. When Grok reads that note, it is reading untrusted input.

  • Read-only is the mitigation. A successful injection can make the bot say something wrong in Discord. It cannot make it write, delete, or reach a tool that does — none exists.
  • Tool descriptions state plainly that returned text is data, not instruction. That is a nudge, not a control; the control is the absent write path.
  • Every call is logged as one structured line (tool, duration_ms, row_count, outcome) to the Vercel log — auditable without a database write, which the read-only role could not perform anyway.

Phases

Phase 1 — shipped in this change

Endpoint, auth, eleven tools, tests

Everything above except the Neon role and the connector registration, both of which are configuration rather than code. Works locally against DATABASE_URL the moment MCP_BEARER_TOKEN is set.

Phase 2 — deploy · blocked

SELECT-only role + Vercel env + connector install

Tooling is ready — npm run mcp:role and npm run mcp:verify — but the endpoint cannot go live yet, and the reason is not this feature:

  • The CRM is not deployed. No Vercel project links to this repository. The one named crm has no environment variables and its only production deployment errored; the account's other 35 projects are client sites. An MCP endpoint on localhost is unreachable from Discord, so a deployment has to exist before there is a URL to register.
  • No database credentials are reachable from this checkout — no .env.local, and the Vercel project holds none — so the Neon role cannot be provisioned from here.

Neither blocks the other work: the endpoint, its tools, and both scripts are complete and verified as far as they can be without a deployment and a database.

Phase 3 — later, only if asked

Revenue tools, then writes

Payments/subscription tools are additive and low-risk. Writes are not an extension of this plan — they need separate tools, a second role with scoped INSERT/UPDATE, per-user or short-lived tokens, and human-in-the-loop via the existing suggestions queue. Do not widen the v1 bearer into write access; supersede this plan instead.

Registration

Remote MCP connector, Streamable HTTP, bearer header. Placeholders on purpose — the real values live in Vercel and in the bot's secret store, never here.

{
  "type": "streamable_http",
  "url": "https://<crm-host>/api/mcp",
  "headers": { "Authorization": "Bearer <MCP_BEARER_TOKEN>" }
}

Smoke test before wiring the bot:

curl -s -X POST "$MCP_URL" \
  -H "Authorization: Bearer $MCP_BEARER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | jq '.result.tools[].name'

Risks

RiskMitigation
Bearer token leaks (bot config, log, screenshot)Blast radius is eleven read tools over five tables. Rotate the env var; no other system shares the secret. Consider rotating on a schedule once the bot is live.
Endpoint accidentally live on a preview deploy with production dataSet the env vars in the production environment only. Unset token → 503.
Unbounded scraping through a valid tokenlimit ≤ 100 per call; no cursor/offset in v1, so bulk export means many logged calls rather than one. Rate limiting deferred (serverless in-memory buckets are theatre) — revisit if the log shows volume.
Fallback to DATABASE_URL silently ships as "read-only"The route logs which URL it resolved on first use, and the plan lists the role as a deploy step, not an optional one.
Schema drift breaks a tool silentlyTools use Drizzle's typed columns, so a renamed column fails npm run build, not production.

Out of scope

  • Any write tool, and any widening of this bearer toward one.
  • A run_sql / arbitrary-query tool, permanently.
  • Proposals, payments, subscriptions, repos, suggestions, agent runs, the graph.
  • MCP resources and prompts — tools only.
  • Per-user identity. The bearer authenticates the bot, not the Discord user behind a question; this is single-tenant CRM data and everyone with the bot sees the same thing, consistent with the app's existing model.
  • SSE / stateful sessions.

Verification

  1. npm run lint, npm test, npm run build.
  2. With MCP_BEARER_TOKEN unset: POST /api/mcp → 503, and nothing hits the database.
  3. With it set: no header → 401; wrong token → 401; correct token + tools/list → eleven names.
  4. tools/call on search_companies with {"query":"scuba"} returns rows; with {"limit":9999} returns 100, not 9999.
  5. Unknown tool name → isError: true result, not a transport error.
  6. npm run mcp:verify -- --url <deployed>/api/mcp --token <token> — nine checks covering all of the above.
  7. The three canonical questions answered end-to-end from Discord.
