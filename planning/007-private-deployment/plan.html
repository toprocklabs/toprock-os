Plan · Feature 007

Private deployment & data migration

Put the CRM on Vercel so the agent can reach it, while the CRM itself has no public face: three paths answer from the internet, everything else returns 404. The UI exists only when you run it locally against the same database.

The requirement, honestly stated

The ask was "hosted on Vercel, connected to Neon, but not accessible on the web except locally." Two halves of that cannot both hold literally: Grok Bot runs in Discord's cloud and cannot reach localhost. Something has to be internet-reachable or the agent has nothing to call.

What can hold, and what this plan builds: the only things reachable from the internet are the machine endpoint the agent needs and the client-facing SOW pages. The CRM — dashboard, accounts, contacts, opportunities, tasks, activities, payments, proposals admin, and the login page itself — returns 404 to the entire internet. It is served only by npm run dev on your machine and your brother's, against the same Neon database.

The strongest property here is that there is no authentication surface in production at all. No login form to brute-force, no session cookie to steal, no password reset to abuse. An attacker who learns the deployment URL finds a bearer-gated JSON endpoint and some PIN-gated proposal pages. There is nothing else to attack, because nothing else answers.

The surface allowlist

PathInternetWhy
POST /api/mcp200The agent. Bearer-gated Streamable HTTP MCP, 12 tools (plan 008).
/api/agent/health, /api/agent/sync-repos200The agent's REST companions, same CRM_AGENT_TOKEN.
/p/<slug>, /p/<slug>/terms, POST /p/<slug>/sign200Clients view and sign SOWs. Already PIN-gated per proposal.
/_next/static/*, /_next/image*, /favicon.ico200Without these the proposal page renders unstyled. See the note below on why this leaks nothing.
/, /login, /accounts, /contacts, /opportunities, /tasks, /activities, /inbox, /map, /payments, /proposals, /customers404The CRM. Local only.
/proposals/<id>/pdf404Signed agreements. Local only.
anything else404Default deny — new routes are private until deliberately allowlisted.

Why allowing /_next/static costs nothing. Those files are compiled client-side JavaScript and CSS. Someone who guessed a chunk filename would get the browser code for, say, the accounts table — which is already published at github.com/toprocklabs/toprock-os, a public repository. No CRM data lives in a static chunk.

Data requests are blocked because they carry the page's own path. React Server Component payloads are fetched as GET /accounts?_rsc=… and server actions POST to the page path. Both are matched on /accounts and 404 like any other request to that route, so no rendered row ever crosses the boundary.

Mechanism: proxy.ts

Next.js 16 renamed middleware.ts to proxy.ts (node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md) and it now defaults to the Node.js runtime rather than Edge. The file exports one function, runs before any route renders, and is the earliest place we can refuse a request.

The decision itself lives in a pure function so it can be unit-tested without booting Next:

// src/lib/public-surface.ts
export function isPubliclyAllowed(pathname: string): boolean

// src/proxy.ts
export function proxy(request: NextRequest) {
  if (isLockedDown() && !isPubliclyAllowed(request.nextUrl.pathname)) {
    return new NextResponse(null, { status: 404 });
  }
  return NextResponse.next();
}

A bare 404 with no body is deliberate: it is indistinguishable from a route that was never built, so the response does not confirm a CRM is there. 403 would advertise that something exists and is being withheld.

The fail-closed rule

Lockdown is on whenever NODE_ENV === "production", unless CRM_PUBLIC_SURFACE=all is explicitly set.

ContextLocked?
npm run dev on your machineNo — NODE_ENV=development. Full CRM, zero configuration.
Vercel productionYes.
Vercel preview deploysYes — and they have no database and no MCP token either (plan 006 sets those on production only).
npm run build && npm start locallyYes, unless you set CRM_PUBLIC_SURFACE=all. Testing a production build of the full UI is an opt-in.

Keying off NODE_ENV rather than VERCEL=1 is the safer default: a deployment anywhere else — a VPS, a container, someone else's Vercel account — is locked too, instead of quietly failing open because one vendor's variable was missing.

What a stranger can see

  1. Hits https://<host>/ → 404. No redirect to a login, no branding, no framework error page.
  2. Tries /login, /admin, /accounts, /api/health → 404.
  3. Finds /api/mcp (it is in the public repo) → 401 without the bearer, and the bearer is 43 random characters that exist only in Vercel's environment.
  4. Finds a proposal slug → the PIN gate, unchanged from what clients already use.

The residual exposure is the same as before this plan: a leaked bearer reaches 11 read-only tools over five tables, and a leaked proposal slug plus PIN reaches one client's SOW.

How you and your brother get in

Both of you run it locally — this was the explicit choice, and it is what makes the 404 wall possible. Setup per machine: clone the repo, npm install, put DATABASE_URL and AUTH_SECRET in .env.local, npm run dev. Both machines talk to the same Neon database, so you see the same data and each other's edits.

The cost of this choice, stated plainly. No phone access, no laptop-without-the-repo access, and adding a third person means walking them through a local setup and handing them a database credential. If that friction bites, the fix is not to open the wall — it is to add exactly one gated route, or put the UI behind Vercel Authentication with team seats. Supersede this plan rather than setting CRM_PUBLIC_SURFACE=all in production, which would expose everything at once.

Data migration

A new Neon project starts empty. The existing CRM data lives in the original Neon project, whose connection string is not on this machine — finding it in the Neon console is the one prerequisite nothing else can substitute for.

scripts/migrate-db.mjs does the copy and then checks its own work:

npm run db:migrate -- --from "$OLD_URL" --to "$NEW_URL" --dry-run
npm run db:migrate -- --from "$OLD_URL" --to "$NEW_URL"
  • Dry run first, always. It connects to both, prints every table with its row count side by side, and says exactly what would be copied.
  • Refuses a non-empty target unless --force. Restoring into a database that already has rows is how you get duplicate accounts and broken sequences.
  • Warns on a pooled endpoint. Neon's -pooler host is for serverless request traffic; a dump or restore should use the direct endpoint or it can drop mid-transfer.
  • Copy is pg_dump --no-owner --no-acl -Fc piped into pg_restore, so roles and grants from the old project do not follow the data into the new one — the MCP role is created fresh there by npm run mcp:role.
  • Verifies afterwards by re-counting every table on both sides and printing a per-table diff. A mismatch exits non-zero. Sequences come across in the dump, so the next INSERT continues from the right id rather than colliding.

The old database is only ever read. Nothing in this process writes to or drops it, so it stays as a fallback until you choose to delete it.

Phases

Phase 1 — shipped

Lockdown + migration tooling

proxy.ts, the allowlist, its tests, and scripts/migrate-db.mjs. Verifiable locally against a production build.

Phase 2 — blocked on the old connection string

New Neon project, schema, data

Create the project, npm run db:push, dry-run the migration, run it, confirm the row-count diff is clean.

Phase 3 — deploy

Vercel env, first deploy, MCP role

DATABASE_URL (new project) into toprock-labs/crm production, then npm run mcp:role and MCP_DATABASE_URL, then deploy and verify the wall from an unauthenticated client.

Risks

Out of scope

  • Any web-accessible CRM UI, gated or otherwise.
  • Vercel Authentication / Password Protection — they would block the agent and the client SOW pages alike.
  • IP allowlisting (Vercel Enterprise only).
  • Multi-tenant authorization. Everyone with the database sees everything, as today.
  • Deleting the old Neon project.

Verification

  1. npm run lint, npm test, npm run build.
  2. Locally: npm run dev serves the whole CRM, unchanged.
  3. Locally: npm run build && npm start → /accounts is 404, /p/<slug> renders with styling, /api/mcp answers.
  4. Against the deployment, from a browser with no cookies: /, /login, /accounts, /proposals all 404.
  5. npm run mcp:verify -- --url https://<host>/api/mcp --token <token> passes all nine checks.
  6. Row-count diff after migration is clean, and the CRM shows the migrated data locally.
