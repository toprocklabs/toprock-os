Plan · Feature 008

Agent MCP hardening

Two MCP implementations were built in parallel and collided on the same route. This records which one survived, why, and the security layer ported onto it: a SELECT-only database role for reads, a classification that makes the read/write boundary testable, and a verifier that checks the whole surface.

The decision, and why

PR #4 stays; plan 006's security layer is ported onto it. Three reasons:

  1. It was already merged and deployed. Reverting reviewed, tested, working code to substitute an uncommitted alternative is churn, not progress.
  2. It does something plan 006 deliberately refused to do, and the refusal was wrong for this product. Plan 006 scoped writes out of v1. But the CRM already has a human-in-the-loop queue — suggestions + /inbox — built exactly so an agent can propose and a human can approve. PR #4 uses it. "The agent keeps the CRM current from meetings and git activity" is the actual goal; read-only was a means, not the end.
  3. What plan 006 had that PR #4 lacked was orthogonal. The role, the connection split, and the wall are not tied to a tool catalog. They port cleanly onto someone else's tools.

What carries over unchanged from plan 006: no generic run_sql tool, ever. PR #4 agrees — its twelve tools are named and hand-written. A Discord message is untrusted input, and named tools keep "this cannot touch users" reviewable rather than merely promised.

What shipped in PR #4

  • Streamable HTTP MCP at POST /api/mcp, with GET returning server info and DELETE ending a session. CORS and Mcp-Session-Id handling included.
  • Ten read tools: list_accounts, get_account, list_contacts, get_contact, list_opportunities, get_opportunity, list_tasks, list_activities, list_suggestions, list_project_repos.
  • Two write tools: propose_suggestion (inserts a pending suggestions row plus an agent_runs row — never a core table) and sync_project_repos (refreshes the GitHub mirror).
  • An auto-apply policy that is off by default: requires CRM_AGENT_AUTO_APPLY=true, confidence ≥ 95, and an allowlist defaulting to log_activity alone. PR #4 also hard-blocked stage_change, new_deal, update_deal and update_account. That hard-block was later removed — those kinds auto-apply when listed in CRM_AGENT_AUTO_APPLY_KINDS at sufficient confidence. Env gates remain.
  • REST companions at GET /api/agent/health and POST /api/agent/sync-repos, same bearer.
  • Tests for auth rejection, payload validation, suggestion shape, MCP initialize/list, and repo-sync planning.

Reviewed and found sound: the token comparison is timing-safe and fails closed when unset, and no tool references users, proposals, or the signed-PDF tables.

The read/write connection split

PR #4 ran every tool on one read/write connection. Now the ten read tools run on a connection whose database role physically cannot write:

export async function dispatchAgentTool(name, rawArgs, db: Db, readDb: Db = db) {
  const readOnly = READ_ONLY_TOOLS.has(name) ? readDb : db;
  …
}

The route supplies getReadOnlyDb(), which reads MCP_DATABASE_URL. Writes — propose_suggestion, sync_project_repos, and the agent_runs bookkeeping around every call — keep the read/write connection and stay gated by /inbox.

The default parameter (readDb: Db = db) means existing callers and tests keep working unchanged, and a missing MCP_DATABASE_URL degrades to the old behavior with a warning rather than breaking the endpoint.

The SELECT-only role

Seven tables, because that is what the read tools actually touch — verified by reading their queries, not assumed:

companies  contacts  deals  activities  sales_tasks  suggestions  project_repos

agent_runs is deliberately absent: it is only ever written, and writes never use this role. Not granted at all: users, proposals, proposal_documents, payments, stripe_subscriptions, relationships, place_enrichment.

npm run mcp:role              # provision, then audit
npm run mcp:role -- --audit-only   # "is it still read-only?", months from now

The script proves the result instead of asserting it, by asking Postgres what the role can do to every table in the schema via has_table_privilege — a catalog read, so the audit itself can never write. Any unexpected privilege prints <-- UNEXPECTED and exits non-zero.

No ALTER DEFAULT PRIVILEGES. Granting SELECT on future tables would hand the agent every table added later — the opposite of an allowlist. A new table must be added to READABLE_TABLES on purpose.

Classification as a test

A split is only as good as its maintenance. tests/agent-tool-classification.test.ts fails the build when:

  • a catalog tool is in neither the read-only set nor the known write list — so a new tool cannot inherit a connection by accident;
  • a write tool is marked read-only;
  • READ_ONLY_TOOLS names a tool that no longer exists;
  • the write surface grows beyond the two approved tools — a third is a real decision needing its own review, not a refactor.

If someone does misclassify a write tool as read-only, it fails loudly against a role that cannot perform the write, rather than silently gaining privileges. That is the safe direction for the mistake to fall.

The verifier

npm run mcp:verify -- --url <host>/api/mcp --token <token> checks the deployed surface end to end: that /, /login, /accounts, /proposals, /payments and /inbox all 404 (the plan 007 wall), that missing and wrong tokens are both rejected, that tools/list advertises exactly the twelve known tools and nothing outside them, that a run_sql call is refused, that an over-large limit is clamped, and that a real read answers. Every request it makes is a read.

Residual risks

RiskStanding
One token covers both read and write toolsAccepted for now. A leaked CRM_AGENT_TOKEN can propose suggestions, which a human must still approve in /inbox. Splitting into two tokens is the next hardening step if the agent's audience ever widens.
Auto-apply could be switched on carelesslyOff by default and still needs three env vars aligned (CRM_AGENT_AUTO_APPLY, kinds allowlist, min confidence). The original hard-block on stage/deal/account kinds was later removed so operators can allowlist those kinds on purpose.
Prompt injection through activity notesUnchanged from plan 006: notes are attacker-influenceable text. The mitigation is that the write path leads to a review queue, not to the database.
sync_project_repos calls GitHub with GITHUB_TOKENRead-only PAT, mirror-only writes into project_repos. Noted rather than mitigated further.

Verification

  1. npm run lint, npm test (111 tests), npm run build.
  2. npm run build && npm start → CRM paths 404; /api/mcp and /api/agent/* answer 503 (token unset) rather than 404; /p/<slug> renders. Confirmed.
  3. npm run mcp:role against the new database, then --audit-only shows SELECT on exactly seven tables and write access nowhere. Pending a database.
  4. npm run mcp:verify against the deployment passes every check. Pending a deployment with credentials.
